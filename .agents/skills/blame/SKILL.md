# Blame - 问题上报与协作升级机制

> **当前阶段：试运行（Trial Phase）**
> 以下为本阶段临时调参，仅试运行期生效；将来取消本阶段时整段删除，不影响下方固有规则：
> - **判定阈值从严**：处于灰色 / 犹豫 / 中间区间时，默认 blame；鼓励上报，宁可多报；
> - 后台有人工持续处理 blame 数据，上报噪声由后台流程消化，Agent 不以上报量成本抑制必要 blame；
> - 试运行期场景规则会随使用情况调整。

## 0. 加载层 vs 触发层

本 skill 由 `AGENTS.md` 强制加载，**规范常驻、始终生效**；是否实际调用 blame 工具由下方 **判定范围** 决定。

- **加载层（Always-Loaded）**：规则本身 100% 生效，Agent 必须遵守。
- **触发层（Conditional-Trigger）**：仅当命中判定范围时，才执行实际的 blame 动作。
- 普通对话 / 顺利推进 → 规范保持生效，但**不触发上报动作**。
- 命中判定范围 → 按 §3 重试观察诊断判定；一旦观察到「一次重试仍未解决」，**必须触发** blame，不得绕过、延期或继续在死循环中重试。

## 1. 术语定义

本文中的 blame 是工程协作中的问题上报动作，不表示自责、归因或任务暂停。

blame 是 Agent 在任务执行过程中、当 §2 判据在现实中显形时，向外部协作系统提交的一次结构化上报。**执行与 blame 没有本质（因果）联系，只有先后（时序）联系**：

- **执行**是 Agent 服务于任务本身的自然动作——其目的在于完成任务，而非为 blame 提供前置依据。第一次叫**执行**，第二次及以后叫**重试执行**，每一次在性质上都只是同等的**执行**。
- 顺利时：执行 → 执行 → 执行 → …（一直执行，不 blame）。
- 不顺利时：执行 → 重试执行 → … → blame。blame 只是「恰好发生在这里」——因为 §2 判据在这一段显形了。
- 我们观察的是**重试的结果**：重试解决了问题 → 顺利路径，继续；重试一次仍未解决 → 应当触发 blame。
- 重试是 Agent 执行任务时的自然动作（执行未解决即自然重试），不是 Agent 裁决「要不要重试」或「是否例外」；本文件是观察与触发机制，不命令重试次数、不裁决例外。

**当前约定：重试一次。** 观察到「一次重试仍未解决问题」时，认定 §2 判据已在现实中显形，应当触发 blame。blame 机制的整体目的是**防止死循环**——一次重试未解决后不得继续重试，应即 blame。

**设计目标：问题必须进入可处理闭环。**

仅记录问题不构成处理闭环。Agent 不得通过写入 AGENTS.md、memory、代码注释或 TODO 的方式替代上报；对需要外部协作的问题，blame 是唯一认可的升级通道。

**执行策略：Proactive。** Agent 主动识别问题、主动执行与重试；一旦观察到「一次重试仍未解决」即提交结构化上报。不得等到问题升级为不可恢复阻塞后再上报；也不得在一次重试未解决后继续重试，形成死循环。

### 场景描述

blame 的状态转移为「**执行 →（重试执行一次未解决）→ 上报 → 后续动作**」：

- Agent 在任务中执行；
- 若执行未解决问题，即自然进入重试；
- 重试解决了问题 → 回到顺利路径，不触发 blame；
- 重试一次仍未解决 → §2 判据已显形，Agent 同步调用 `ai blame` 命令；
- 等待命令本身返回（命令是同步的）；
- 命令返回 ok 与 blame id 后，blame 视为成功；
- blame 成功后，Agent 不等待人类回复，应根据风险级别、上下文完整性与任务目标选择继续、降级、暂停或退出；

## 2. 判定范围（什么问题必须触发 blame）

> 待补充：后续通过案例逐步定义具体的判定规则。

一级分类骨架（占位，待案例细化）：

- **信息缺失**：执行所需的关键信息不在上下文中，且无法通过现有工具自取
- **决策歧义**：存在多个合理方案、选择会显著影响产物，且 Agent 不具备裁决依据
- **执行受阻**：工具/环境/权限失败，Agent 无法独立恢复
- **风险越界**：触及高危操作、生产环境、不可逆变更
- **产物存疑**：接手的上游产物（其他 Agent 或历史代码）与预期不符

**判定阈值**：

- 明确命中上述任一分类 → blame。
- 是否命中不明确（灰色区间）→ 按 §3 重试观察诊断判定：执行并重试，若一次重试仍未解决 → blame。
- 试运行阶段的从严调参见文首「试运行」段。

### 2.1 案例：工具相关的执行受阻

以下三类场景均归入 **执行受阻**。Agent 应先执行并重试确认；重试后仍受阻时必须 blame，**不得**通过更新 AGENTS.md / memory / 注释绕过：

1. **工具选型空白**：已知工具都不适用，不知道选什么工具解决问题。
   - ❌ 禁止：随机选择不确定工具继续执行 / 留 `# TODO: 找个工具`
   - ✅ 要求：执行确认现有工具边界；重试后仍无可用工具则 blame，Category=执行受阻，Ask=请指定可用工具或方向

2. **工具不存在**：建议的工具在本地找不到，也找不到类似替代品。
   - ❌ 禁止：自行 `npm install` / `brew install`（被 steering 禁止）/ 写进 AGENTS.md「下次记得装」
   - ✅ 要求：执行确认命令或等价工具是否存在；重试后仍不存在则 blame，Category=执行受阻，Ask=请安装 X 或指定替代方案

3. **工具调用出错**：已找到工具，但调用失败，重试后仍无法独立恢复。
   - ❌ 禁止：无限重试 / 未说明风险即降级 / 静默跳过
   - ✅ 要求：执行并重试恢复；仍无解即上报，**不得**反复重试拖延

**关键原则**：上述场景下，AGENTS.md 自带的「找不到命令时问用户并建议写进 AGENTS.md」指引在本项目中**被 blame 覆盖**。重试后仍受阻则 blame，不得将写入文档或 memory 作为问题处理闭环。

## 3. 执行流程：观察重试结果 → Call → Wait → Continue/Exit

### 观察重试结果（Observe Retry Outcome）

- Agent 在任务中执行；执行与重试都是 Agent 服务于任务本身的自然动作，不是 blame 的前置工序。
- 执行解决了问题 → 继续正常任务，不触发 blame。
- 执行未解决 → 即自然重试：
  - 重试解决了问题 → 回到顺利路径，不触发 blame；
  - 重试一次仍未解决 → §2 判据已显形，立即进入 Call；
  - 重试超过一次仍未解决 → 反模式（死循环），应在一次重试未解决时即 blame。
- 未发生任何重试即 blame → 反模式（诊断未建立）。
- `### Executed` 必须记录执行与重试的动作及结果，并说明是否在一次重试后仍未解决；确实无法执行 / 重试时，应写明原因。

### Call

**前置：获取 appId 与 planId**

blame 路径形如 `/<appId>/<planId>`（planId 已知时）或 `/<appId>`（planId 未知时）。二者**必须**真实有效，不得编造占位符。取值规则：

- **appId**：首选读取仓库内 `.context/current-plan-metadata.yaml` 的 `appId` 字段（READONLY METADATA，由上游系统注入）；若该文件不存在 / 字段缺失，使用**当前工作目录的最后一段（项目名）**——此值 Agent 自身环境可知，无需脚本获取。
- **planId**：首选读取 `.context/current-plan-metadata.yaml` 的 `planId` 字段；若不存在 / 缺失，**直接省略**，路径退化为 `/<appId>`，命令本身兼容此形式。
- 通常 appId 与 planId 同源：metadata 缺失时两者皆缺，此时路径即 `/<项目名>`，例如 `ai blame /cms-mgr --title ... --context ...`。

**命令模板**：

```bash
ai blame /<appId>/<planId> --title "<问题标题>" --context "<结构化上下文>"   # planId 已知
ai blame /<appId>        --title "<问题标题>" --context "<结构化上下文>"   # planId 未知
```

示例：

```bash
ai blame /cms-mgr/PLAN-102 --title "Upload Image 接口字段命名应采用 snake_case 还是 camelCase" --context "### Category
决策歧义

### Where
cms-mgr/PLAN-102 / api/upload_image.go:42

### Observed
现有接口同时存在 snake_case（image_url）与 camelCase（imageUrl）两种命名，Upload Image 是该 PLAN 新增的第一个端点，无既定先例可循。

### Expected
PLAN-102 或 cms-mgr 仓库内应有统一的 JSON 字段命名规范，便于直接套用。

### Executed
1) grep cms-mgr 内 *.go 发现两种风格共存，比例约 6:4；
2) 查 docs/api-style.md 未命中；
3) 询问 codex agent，无明确答复。
以上执行与重试后，决策歧义仍未解决。

### Ask
- PLAN-102 的对外 JSON 字段应采用 snake_case 还是 camelCase？
- 是否需要同时落地一份 docs/api-style.md 作为后续基准？

### Impact
重试后仍存在决策歧义；blame 后 Agent 将根据风险级别选择暂停或继续低风险推进。"
```

字段之间使用**真实换行**分隔（双引号内直接回车）。**不要**在双引号内写字面 `\n` —— shell 不会把它展开为换行，服务端将原样存为反斜杠+n 两个字符。

- 路径参数：blame 必须挂在某个 Plan 下，路径形如 `/cms-mgr/PLAN-102`（planId 已知）或 `/cms-mgr`（planId 未知）。`appId`、`planId` 取值按上方「前置」规则，**不得编造**。
- `--title`：一行普通文字短句，能让人快速识别问题。**不得带任何前缀标签**（如 `### Category`、`[BLAME]`、`[BUG]` 等），也不得使用 Markdown 格式。分类信息放在 `--context` 的 `### Category` 段，不在 title 重复。
- `--context`：Markdown 文本，使用三级标题分段，见第 4 节模板。

### Wait

- 命令是**同步**的；必须等待命令返回。
- **只有**返回 ok **且**拿到 blame id，blame 才算成功。
- 命令失败 → blame 未成功，不得在对话中谎称已 blame，不得编造 blame id；应在回复中如实告知命令失败，附上完整命令与报错，然后退出。

### Continue/Exit

- blame 成功后，Agent 不等待人类回复。
- Agent 应在回复中声明 blame id，简洁说明已上报的问题内容，供人类快速了解。
- 后续动作由 Agent 根据风险级别、上下文完整性与任务目标判断：可以继续低风险推进、降级推进、暂停等待或退出任务。
- 若继续推进，不得围绕同一个未解决问题继续重试（死循环）；遇到新的独立问题时，重新按「执行 → 重试观察 → 上报」流程处理。

## 4. `--context` 结构化模板

后端以 Markdown 格式存储 context，模板固定使用 Markdown **三级标题** 作为字段分段，缺失项内容写 `N/A`，**不得整段省略**；Agent 之间据此一致解析。

各字段之间用**真实换行**分隔（在 shell 双引号内直接回车），传给 `--context`。**不要**使用字面 `\n`——shell 不会展开，服务端将原样存为反斜杠+n 两个字符，破坏 Markdown 渲染。

```markdown
### Category
<信息缺失 | 决策歧义 | 执行受阻 | 风险越界 | 产物存疑>

### Where
<文件路径:行号 / 命令 / 任务阶段 / URL；可附相关 blame id / commit / PR / 文档链接，无则不写>

### Observed
<实际观察到的现象，事实描述，不加推测>

### Expected
<按上下文/规范本应是什么样>

### Executed
<Agent 执行与重试的动作及结果；说明是否在一次重试后仍未解决；若无法执行/重试写「未执行，原因：...」>

### Ask
<希望协助/求助/询问的具体问题，一条以上用 - 列出>

### Impact
<若不解决会对任务造成什么影响；以及 blame 后 Agent 计划继续、暂停还是退出>
```

字段约束：

- 三级标题必须为英文且首字母大写（`### Category` / `### Where` / `### Observed` / `### Expected` / `### Executed` / `### Ask` / `### Impact`），顺序不得调换。
- 标题与正文之间换行；段与段之间留一个空行，便于后端 Markdown 渲染。
- `### Observed` 只写事实，不写解释。
- `### Ask` 必须是**可回答**的问题或**可执行**的请求，不得是「请看看」式开放表述。
- `### Impact` 必须说明不解决的影响，以及 blame 后 Agent 计划继续、暂停还是退出；如确实只是提示性上报（不影响主流程），需在 Impact 中明确写出。

## 5. 对话中引用规则

- blame 成功后获得 blame id，形如 `BLAME-005`（工具返回的完整字符串，包含 `BLAME-` 前缀与序号）。
- 对话中再次提及该问题时，**首次提及**使用 `` `[BLAME-005] <问题简述>` `` 格式标注（直接用完整 id，不再外加 `#`）。
- 重复提及同一问题时可简写为 `BLAME-005`。
- 同一问题在同一任务内**不重复 blame**；如已 blame 过，引用旧 id 即可。

## 6. 反模式（禁止行为）

按流程阶段分组：

**A. 诊断阶段：该 blame 时不上报**

- ❌ 命中判定范围（含边界 / 不确定状态）、一次重试仍未解决，却不上报，转而自行假设结论、猜测性实现或部分推进。
- ❌ 重试超过一次仍未解决却不 blame，继续重试形成死循环。

> 自检信号：当回复出现敷衍式极简短句（如「完成了」「明白了」「对不起」）时，往往伴随漏报——应回查是否漏 blame。

**B. 诊断阶段：不该 blame 时上报**

- ❌ 未发生重试即 blame（诊断未建立），导致 `### Executed` 缺少可审计上下文。

**C. 上报内容**

- ❌ 把多个独立问题塞进同一次 blame。
- ❌ 把问题**记录**到 AGENTS.md / memory / 代码注释 / TODO 当作「已处理」。记录 ≠ 解决，blame 才是解决通道。
- ❌ 以上报量成本为由抑制必要 blame。

**D. 谎报 / 伪造**

- ❌ 命令未返回 ok 就在对话中声称 blame 成功。
- ❌ 没有 blame id 就在对话中编造 `[BLAME-...]` 引用。

**E. blame 后处置**

- ❌ 未评估风险级别与任务上下文，直接无条件退出或无条件继续。
- ❌ 等待用户回复才决定后续动作。
