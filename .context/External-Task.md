## 1. 需求复述（确认理解）

1. **两个 Task 必须区分**，不能混为一谈：
   - **External Task**：由外部 Agent 执行，有外部进度控制，OpenCove 不介入执行、不规定内容、不定义枚举。黑盒。
   - **OpenCove Task**：OpenCove 内的 `TaskNodeData`（画布节点），不执行业务，只观察 External Task 是否完成。
2. **OpenCove 的 Task 用 Agent 去观察**：观察动作由 OpenCove 的 Agent 节点执行（live CLI session in PTY），由 Agent 去探测 External Task 的完成信号，OpenCove 只消费 Agent 输出。不是 OpenCove 自己直接读文件。
3. **完成信号 = True/False 布尔**：OpenCove Task 只需观察「完成 / 未完成」，不观察进度百分比、阶段、内容。
4. **OpenCove 不规定 External Task 的枚举与语义**：包括完成信号落在哪、以何形式表达，都是 Agent 的探测能力范畴（提示工程 / provider 能力），非 OpenCove 架构问题。
5. **cron 是架构层关切**：不讨论"App 关闭"这类防御场景，从架构本身的设计讨论 cron 应安排在哪一层。

## 2. 架构事实（已核源码）

以下事实是讨论归属的依据，均经 main 分支核查。

### 2.1 truth owner

- `task.status` 的权威写入**只经** Control Surface `node.update`（`kind:'task'`），handler `src/contexts/workspace/application/nodeControl/nodeControlUpdate.ts:145-153`，落 SQLite（`workspaces` 表）。
- Worker 是 durable truth owner（`src/app/worker/index.ts`、`src/app/worker/userData.ts`，RUNBOOK 附录 §主体功能运行位置）。
- 外部 HTTP client 可经 `/invoke` 调 `node.update` 写 `task.status`，不经过 Renderer（`controlSurfaceHttpServer.ts:321-362` + `nodeControlUpdate.ts:18-55`）。

### 2.2 Agent 启动与输出观测的现有层

- Agent 启动是 Control Surface 命令 `session.launchAgent`（`sessionHandlers.ts:121`），在 Worker 侧执行；Renderer 只是调用方。
- PTY runtime 在 Worker（`createHeadlessPtyRuntime`，`src/app/worker/index.ts`）。
- Agent 输出观测的现有范式 `SessionTurnStateWatcher`（`src/contexts/agent/infrastructure/watchers/SessionTurnStateWatcher.ts:120`）由 `src/contexts/terminal/presentation/main-ipc/sessionStateWatcher.ts:334` 实例化，**跑在 Worker/Main 进程**：
  - `fs.watch` JSONL + 增量解析（`:144-162, :223-265`）
  - 经 `onState(sessionId, state)` → `broadcastSessionState` → IPC `ptyState` 推送（`sessionStateWatcher.ts:176-187`）
  - Renderer 经 `ptyEventHub.onState` 消费（`ptyEventHub.ts:178-182`）
  - session-scoped, agent-only：`usePtyTaskCompletion.ts:22` 早 return 非 agent 节点，**不写 task.status**。

### 2.3 现有周期机制

- Worker 无 scheduler 抽象。现有 ad-hoc `setInterval`（`.unref()` + 手动 dispose）：
  - parent-PID liveness probe 1s（`src/app/worker/index.ts:235-243`）
  - SSE 重连 backoff 750ms（`workerSyncBridge.ts:192-194`）
  - SSH readiness poll 150ms（`managedSshEndpointRuntime.ts:145`）
- 无 `scheduler` / `registry` / `registerPeriodicJob` / `cronJob` 抽象（`src/app/main`、`src/app/worker` 检索未发现）。
- `system.ping` 是 on-demand 查询，不是周期 ticker（`systemHandlers.ts:14-24`）。

### 2.4 Task 现有数据模型与写入路径

- `TaskNodeData`（`src/contexts/workspace/presentation/renderer/types.ts:69-81`）字段：`requirement` / `status` / `priority` / `tags` / `linkedAgentNodeId` / `agentSessions` / `lastRunAt` / `autoGeneratedTitle` / `isEnriching?` / `createdAt` / `updatedAt`。**无观察配置字段**（无 watchSource / filePath / pollInterval / cursor）。
- `task.status` 现有 writer（共 9 处，全在 Renderer 侧 + 全由用户动作或 Agent 节点生命周期触发）：
  - Footer 用户选择（`useTaskActions.ts:187-212`）
  - Run reuse / new（`useTaskActions.agentSession.run.ts:87,260`）
  - Resume（`useTaskActions.agentSession.resume.ts:184`）
  - 节点关闭 / 删除（`useNodesStore.closeNode.ts:62`、`useApplyNodeChanges.ts:255`）
  - 创建 / Note→Task 默认（`useNodesStore.createNodes.ts:305`、`useNoteToTaskConversion.ts:120`、`nodeTransform.ts:97`）
- `applyAgentStateToNodes`（`usePtyTaskCompletion.ts:15-53`）只写 agent 节点 `data.status`，**不写 task.status**（`:22` 早 return 非 agent 节点）。
- `TaskRuntimeStatus = 'todo'|'doing'|'ai_done'|'done'`（`types.ts:28`），无 progress 百分比 / 失败 / 超时枚举。

### 2.5 Renderer 侧文件轮询范式（参考，非 truth 路径）

- `useDocumentNodeExternalRefresh.ts:24-179`（Renderer 侧）是 repo 唯一的"画布节点轮询外部文件"范式：
  - `window.setInterval(runCheck, intervalMs)` + `window.opencoveApi.sync.onStateUpdated` + `filesystem.stat` 触发
  - 决策 `resolveDocumentNodeExternalRefreshDecision`（`DocumentNode.sync.ts`）：`unchanged` / `conflict` / `refresh`
- **性质**：UI 刷新关切（让 Document 节点内容显示不陈旧），**不是 durable truth 变更关切**。Document 节点不写入 SQLite 的 truth 字段。Task status 是 durable truth，不应套用 Document 范式。

### 2.6 文件系统访问能力（已具备，但与 cron 无关）

- `filesystem.readFileText(InMount)` / `readFileBytes(InMount)` / `stat(InMount)` / `readDirectory(InMount)` 受 mount-root + approved-roots 双重边界（`fileUriScope.ts:52-77`、`filesystemMountSupport.ts:117-127`）。全为 one-shot，无 stream/subscribe。
- 无 `chokidar` / `node-watch`；唯一 `fs.watch` 在 `SessionTurnStateWatcher.ts:152`（agent session log，agent-only）。
- 无 Control Surface 命令以 SSE / WebSocket 流式推送文件变更事件。

## 3. 概念边界（两层 Task）

| 维度 | External Task | OpenCove Task |
|---|---|---|
| 执行者 | External Agent（OpenCove 之外） | 不执行业务，仅观察 |
| 进度控制 | External Agent 自管，黑盒 | 不观察进度细节，只观察完成布尔 |
| 完成信号形态 | 由 External Agent 决定（落文件 / 跑命令 / 调 API） | 由 OpenCove Agent 节点探测后回写 |
| 枚举 / 阶段 | OpenCove 不规定 | OpenCove 不规定（不在架构关切内） |
| 是否进 SQLite | **否** | **是**（`TaskNodeData` 在 `workspaces` 表） |
| 是否有 Control Surface 命令 | **否** | **是**（`node.update`、`session.launchAgent` 等） |
| OpenCove 是否建模 | **否**——它是一团"emits boolean"的外部黑盒 | **是**——是画布节点 + durable state |

**关键约束**：OpenCove 架构只对后者负责。前者是 OpenCove Agent 节点的探测目标，其形态属于 Agent 的提示工程 / provider 能力范畴，**非 OpenCove 架构问题**。

## 4. 架构归属论证

### 4.1 cron 归属层

基于 §2 事实推导：

1. **truth 写入的归属原则**：`task.status` 是 Worker 的 durable truth（§2.1）。任何周期性变更 truth 的调度，应与 truth 同层——否则会跨越进程边界去改 truth（Renderer 调 `node.update` 已是边界跨越，但这只为响应用户动作，不是常态 cron）。常态 cron 跨进程写 truth = 架构异味。
2. **Agent 输出观测层的先例**：`SessionTurnStateWatcher` 已在 Worker/Main 层实例化（§2.2），说明"解析 Agent 输出 → 产出 OpenCove 可消费的状态"这一动作本就归 Worker 层。新增 True/False 探测器与之同层最自然。
3. **Agent 启动链路归属**：`session.launchAgent` 是 Worker 命令（§2.2）。cron tick 启观察 Agent，复用此命令，调度器应在能直接调用此命令的层。
4. **Renderer 是 view/client**：Document 节点轮询范式（§2.5）是 UI 刷新关切，不写 durable truth。Task status 是 durable truth，不应套用 Document 范式。

**结论**：cron 归 **Worker / Control Surface 层**，与 `SessionTurnStateWatcher`、`session.launchAgent`、`node.update` 同层。一个新调度组件周期性触发「启观察 Agent → 解析 True/False 输出 → 经 `node.update` 写 task.status」，全程不离开 Worker 进程，不新增 truth 写入路径（复用现有 `node.update`）。

### 4.2 观察动作的归属层

"OpenCove 的 Task 用 Agent 去观察" 的实现归属：
- 观察 Agent 是 OpenCove Agent 节点（`AgentNodeData`，`types.ts:53-67`），即一个 live CLI session in PTY，由 `session.launchAgent` 启动。
- 该 Agent 与 OpenCove Task 的 linkage 已有范式：`task.linkedAgentNodeId` ↔ `agent.taskId`（`types.ts:66,74`，RUNBOOK 附录）。
- 现有 `reuseLinkedAgentForTask`（`useTaskActions.agentSession.run.ts:21-102`）已实现"复用已 linked 的 Agent 节点重发 prompt"语义——cron tick 即"定时重跑 linked agent"。这条语义链已存在，只是当前由 Renderer 驱动；架构上把它提到 Worker 侧触发不引入新概念。

### 4.3 True/False 探测器的归属层

- 范式对照：`SessionTurnStateWatcher` 把 Agent JSONL 输出解析为 `TerminalSessionState`（`'working'|'standby'`）经 `onState` 推送（§2.2）。
- 新增 True/False 探测器照此层结构：在 `SessionTurnStateDetector` 旁新增一类 detector，把 Agent 输出的 boolean 信号映射为 `task.status` 的目标值（如 `done` / `todo`）。
- 与 SessionTurnStateWatcher 的差异：SessionTurnStateWatcher 的输出是 agent 节点状态（`data.status`）；新探测器的输出是 **task 节点状态**（`task.status`），并经 `node.update` 落 SQLite。这是新输出通道，但复用 `node.update` 的写入路径。

## 5. 架构可行性结论

### 5.1 可行性判定：**可行**

理由（基于复用现有架构，无新真值路径）：

1. **不新增 truth 写入路径**：cron tick → `node.update`（现有）→ SQLite。外部 Agent 写 task.status 走的也是这条路径，cron 走同一条，一致性满足。
2. **不新增跨进程边界**：调度器、Agent 启动、输出探测、truth 写入全在 Worker 层，无 Renderer 介入。
3. **不新增 Agent 集成协议**：观察 Agent 是已注册 provider（`claude-code`/`codex`/`opencode`/`gemini`，`agentSettings.providers.ts:1`），不需要把 External Agent 注册为 provider——External Agent 是被探测对象，不是 OpenCove 的 provider。
4. **不破坏 worktree 禁用约束**：观察 Agent 在 Space 的 cwd 内运行，与 RUNBOOK 附录「不允许使用 Worktree」结论兼容。
5. **linkage 范式已存在**：task↔agent 双向 linkage（`linkedAgentNodeId` ↔ `taskId`）已是源码事实，观察 Agent 即一个被 task 链接的 agent 节点。

### 5.2 复用点（已具备，无需新建）

| 能力 | 现有锚点 |
|---|---|
| Agent 启动 | `session.launchAgent`（`sessionHandlers.ts:121`） |
| Agent↔Task 复用语义 | `reuseLinkedAgentForTask`（`useTaskActions.agentSession.run.ts:21-102`） |
| task.status 写入 | `node.update`（`nodeControlUpdate.ts:145-153`），支持外部 HTTP `/invoke` |
| Agent 输出观测范式 | `SessionTurnStateWatcher`（`SessionTurnStateWatcher.ts:120`）+ `SessionTurnStateDetector` |
| linkage 双向指针 | `task.linkedAgentNodeId` ↔ `agent.taskId`（`types.ts:66,74`） |

### 5.3 架构 gap（req 定后再设计，此处只命名，不展开）

| Gap | 性质 | 架构影响 |
|---|---|---|
| Worker 层无 scheduler 抽象 | 现有 ad-hoc `setInterval` 散落无统一封装 | 需新增周期调度组件，规范化 `setInterval`+`.unref()`+dispose；不破坏现有 truth 路径 |
| `TaskNodeData` 无观察配置字段 | 当前 linkage 是 Agent 节点，观察配置（绑哪个 Agent / 周期 / 观察提示）无字段承载 | 需扩 `TaskNodeData` + DTO 迁移；属 schema 变更（Large，按 DEVELOPMENT.md 须走 Spec） |
| cron tick → reuse-linked-agent 链路当前由 Renderer 驱动 | `reuseLinkedAgentForTask` 在 Renderer hook 内 | 需把同一动作的触发提到 Worker 侧；动作语义不变，触发层变 |
| True/False 探测器不存在 | `SessionTurnStateDetector` 只产 `working`/`standby`，不产 task 状态 | 需新增一类 detector；与现有 detector 同层，新输出通道 |
| cron 触发的 `node.update` revision 抖动 | 每次 tick 写 status 都 bump app_state revision | 若 tick 间 status 未变应跳过写入（幂等 gate）；架构上需在调度层做去抖，避免 SSE 风暴 |
| External Task "落在外部某处" 的探测形态 | OpenCove 架构不规定 | **边界外**——属 Agent 提示工程 / provider 能力，OpenCove 架构不介入 |

### 5.4 不需要新建的能力（澄清，避免误判）

- **不需要**把 External Agent 注册为 OpenCove provider。External Agent 是被探测对象，不是 OpenCove 的执行 provider。OpenCove 的 provider 仍是 `claude-code`/`codex`/`opencode`/`gemini`，观察 Agent 用其中之一执行探测。
- **不需要** OpenCove 直接读 External Task 的进度文件。读探测是观察 Agent 的职责，OpenCove 只消费 Agent 的输出（与 SessionTurnStateWatcher 范式一致——它读的是 Agent 的 session log，不是外部业务文件）。
- **不需要**新增 External Task 的 DTO / 表 / handler。External Task 不进 SQLite，OpenCove 不建模它。

## 6. 未决项（req 未定）

以下 req 定后再进入实现设计，本文件不展开：

1. 观察配置字段的具体形态（绑哪个 Agent 节点 / tick 周期 / 观察提示 / 是否复用 vs 每次新建 Agent）。
2. True/False 信号在 Agent 输出中的表达约定（OpenCove 不规定 External Task 枚举，但需规定观察 Agent 如何输出布尔，以便探测器解析——这属 OpenCove 与观察 Agent 的契约，非 OpenCove 与 External Task 的契约）。
3. status 映射规则（True → `done` / `ai_done`？False → `todo` / `doing`？是否引入 `failed` / `timeout`）。

6. cron 调度组件的生命周期（随 Worker 启停 / 随 Task 节点创建销毁 / 全局唯一 vs 每 Task 一个 ticker）。
